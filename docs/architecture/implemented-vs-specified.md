# Implemented vs Specified

**Status:** runtime honesty for `main`. Fail-closed: a library, test harness, OpenAPI path, or dispatch-preparer is **not** a live capability.

**Grounding:** Enterprise architecture gap analysis (2026-09-21, review SHA `e4d0c9d`, finding **I3**) plus current code and docs. Epic G / phase G.0. This page is G.0.2.

This repository is a **security-hardened prototype with a production veneer**, not an enterprise-ready platform. Specified contracts stay normative for how the product *must* work when a slice ships. They do not mean that slice runs today.

## Hard lines (unchanged)

Do not weaken these because a capability is unimplemented:

| Line | Rule |
| --- | --- |
| YAML SoT | `flowforge/v1` is the only persisted workflow definition. Canvas is a projection. Invalid YAML never guesses a graph. |
| Drafts never run | Publish (or an explicitly approved published test version) then start. Organizing or editing a draft does not make it live. |
| Vault | Display-name + UUID only in chrome, search, and APIs. No KEK, PEM, password, or secret material in browser, room, YAML, logs, or `localStorage`. |
| ADV-021 | Embed chrome from `GET /session` `session.embed` only. Host query is display-only. Missing bind is a visible alert. |
| ADV-024 | Membership / isolation stay grant-gated. Isolation success is a **denial**. |
| Fail-closed authz | Server-derived workspace scope. Host-supplied workspace IDs are `400`. Cross-workspace UUIDs are `404`. |
| Not an n8n clone | Parity of interaction and coverage, not pixels, orange, or a marketplace. |

## Vocabulary

| Status | Meaning |
| --- | --- |
| **Runs today** | Shipped on the default compose or API path and used by operators or hosts. |
| **Partial** | API, chrome, or library exists; the production caller, scheduler, or provider call does not. |
| **Specified only** | Documented contract and/or in-repo engine. Nothing in a shipped deployment invokes it for real work. |
| **Deferred** | Explicitly not this phase (named stub or later epic). |

## Provider execution

`cmd/runner` is production-locked and calls the engine packages. Compose `cmd/worker` does not.

- Do say: the production runner dispatches `kubernetes.*`, `ssh.run`, `script.python` / `script.go`, and `http.request` / `notification.webhook` after a published pin, HMAC ticket, and fence.
- Do say: compose still fails those nodes with `local-worker-unsupported`.
- Do **not** say clusters, SSH hosts, or webhooks are reachable from `deploy/k8s` until an operator adds that provider egress. Script Jobs are created only after `CONTROL_PLANE_API_CIDR` (or a same-namespace Service) is set and `flowforge-script-runner` allows DNS plus that destination. Default-deny stays. A world CIDR is rejected.
- Engine references ([Kubernetes](../reference/kubernetes-engine.md), [SSH](../reference/ssh-engine.md), [script](../reference/script-engine.md)) describe the libraries the runner calls.

Executable on compose today: **6 of 18** defined node types (`flow.condition`, `flow.stop`, `flow.fail`, `data.set`, `data.map`, `data.validate`). Non-executable on that worker: provider nodes, `flow.delay`, plus registry-disabled `data.filter` / `data.merge` / `data.sort` / `flow.join` / `flow.parallel` / `flow.switch`. `flow.approval` waits in the API. The production runner also evaluates those six core nodes. Claim resolves wired inputs for both workers from the latest succeeded `output_redacted` of the claimed node's upstream nodes, the incoming-edge closure. A node with no incoming edges does not read step outputs. A satisfied edge sets `inputs[to_port]` from that output's `from_port`. An edge that did not fire leaves the key absent. `flow.delay` forwards a shared passthrough: a map passes through, a scalar is wrapped as `{"value": ...}`, and an unwired input is `{}`. That shape checks the 16 KiB cap and does not classify redacted upstream keys. An oversized body fails the next step with `output-too-large`, and the message names the delay node. `flow.approval` forwards its resolved `request`, or `{}` when that port is unwired. The approval decision stays on the gate output. A required port whose edge did not fire on a `join: any` step fails with `upstream-skipped`. No publishable core node reaches that failure today. The production runner parks `flow.approval` and inserts the approval in that same transaction with `expires_at` copied from the wait deadline, and parks `flow.delay` with `WaitJob` until the duration elapses (not an in-process sleep). Gate expiry closes that approval in the same transaction. Decide after the gate is no longer `waiting` is `409` `approval_closed` and does not record an approval. Decide rebuilds the approver role and the policy binding or pin from the pinned workflow version and authorizes against that requirement. A version lookup failure, an evaluation failure, or a missing requirement denies the decision and records nothing. When the stored row differs, that correction commits before a 403, including when the caller is not the required role. API, runner, and compose startup (the API process compose runs) resync every pending approval, one transaction per workspace, as `flowforge_app` under RLS. A row that cannot be rebuilt is canceled with `closeReason` `requirement_unresolvable` and no decider. That reason means the version lookup, the policy evaluation, or the matching requirement is missing. If that leaves a waiting gate, the same transaction fails the gate step and job with error code `requirement_unresolvable` and rolls the run up with `rollupExecutionTx`. A sibling already queued, claimed, or running finishes, then the run is `failed` with `requirement_unresolvable`, which frees the concurrency slot. Nothing downstream runs, including a step wired to `expired`. A missing or deleted workflow still fails the run with `workflow_deleted`. A database, network, context, or timeout failure is not that reason: decide returns `503` `approval_requirement_unavailable` with `Retry-After: 5`, records nothing, and changes nothing. The problem document has no `errors` array. Boot resync skips the row so the approval stays pending and the run stays waiting. Compose and the production runner both fail a claim of an unresolvable gate with `requirement_unresolvable` through `FailJob` and `rollupExecutionTx`, so lease recovery does not resume it on `expired`. A transient claim releases the job back to queued and sets `available_at` to now plus 30s plus up to 5s of jitter. When a pending approval already exists for the gate, the outer limit is that row's `expires_at`. Otherwise the limit is the gate-ready time plus the parked-approval wait duration: the step `expiresIn`, or `PT1H` when that field is missing or not a duration, and never longer than the existing `P7D` maximum. The gate-ready time is not the job's `available_at` or `updated_at`. Those columns are set when the job leaves `blocked` and then rewritten by claim, release, and recovery. The ready time is the latest usable `finished_at` of satisfied upstream edges in the same execution. Only the final attempt of each upstream node counts: a success uses that attempt's `finished_at`, and a skip counts only when `finished_at` is set and not earlier than the run's `started_at`. A missing or earlier skip stamp is ignored, and a failed earlier attempt is ignored. The ready time is never earlier than `started_at`. A root gate, or a gate whose upstream left no usable settle time, uses `started_at`. `execution_jobs` has no `finished_at`; that step column is the finish time of the upstream job. A missing gate-ready time with no pending approval has no limit. Those timestamps are not rewritten by a transient release, a lease-recovery requeue, or a later claim. The parked approval's `expires_at` is claim time plus that same wait duration. Evaluation still fails a claim that has no `expiresIn`, so the runner does not park that gate. Past the limit the same transaction fails the job and step with `requirement_unresolvable`, cancels a pending approval for that execution and node with `close_reason` `requirement_unresolvable`, and rolls the run up. The gate does not take `expired`. A waiting gate that already has a pending approval and no transient failure still takes the `expired` port at its deadline. `attempt` is unchanged. Other releases are not delayed. A correction of the approver role or policy pin writes approval event `corrected` with the previous and new values, on decide and on resync. Resync rebuilds a pending row from the run's pinned version and that requirement's policy pin, never from current heads, and does not invalidate it at boot. A gate with no policy does not pick up another pin. Decide still checks freshness against current heads. Lease recovery requeues a claimed approval that has no pending row, without burning the attempt, instead of parking it as waiting, and applies that same delay. SQLSTATE 42501 on a version or policy lookup stays transient, so decide returns 503 `approval_requirement_unavailable` and the row stays pending. A second resync is a no-op. Resync errors are logged and do not block startup; decide remains the backstop. `GET /approvals?status=pending` returns only rows the caller can decide from the stored requirement. Compose still fails `flow.delay`. A step retry is refused unless the run is `failed` or `indeterminate` and the latest attempt of that step started and ended `failed` or `indeterminate`. A soft-deleted workflow and an SSH or script step that is not retry-safe both refuse with `execution_not_retryable` (`workflow_deleted` or `retry_not_allowed`). Cancel and `workflow_deleted` close pending approvals in the same transaction. Memory cancel closes pending approvals with `run_canceled` as well. The execution page shows Retry only when `capabilities.retry.allowed` is true, and a plain reason when that flag is false. A missing or malformed capability hides Retry. A gate on a canceled or failed run follows the step's terminal status and does not offer approve or reject. A retry conflict uses that same plain reason: a canceled run says the run was canceled. When the pinned workflow version is missing (HTTP 404), the page keeps the header, status, steps, and approvals, and says the workflow was deleted so its graph is no longer available. Another version-lookup failure stays an error and is not treated as deletion. Start and operator links stay hidden on that missing version. Retry still follows `capabilities.retry` only. A decide that returns 403 because the pinned gate needs a different approver shows a plain sentence, hides the decide controls, and refetches the approval and the execution. A 409 `approval_closed` stays the existing closed sentence. A failed `flow.approval` step uses the generic failed wording for any error code, including `requirement_unresolvable` and one the UI has not seen before. A 503 `approval_requirement_unavailable` with `Retry-After` and no `errors` array stays a generic error and leaves the decide buttons visible. A `corrected` approval event renders as a line.
